## Concrete findings

No blocking defect was found in the inspected implementation.

- `packages/auth/src/firebase.ts:103` calls the real verifier with revocation checking enabled. The installed Firebase Admin implementation verifies the JWT and, when this argument is true, checks current Firebase user disablement and token revocation. Local claim validation adds the configured project, Google provider, verified-email, subject, timestamp, and unsupported-tenant constraints; it does not substitute for SDK signature verification.
- `packages/auth/src/firebase.ts:98` checks expired/disposed/emulator state after both asynchronous boundaries. Independent probes confirmed that an emulator or disposal transition during verification suppresses SQL lookup, disposal during a SQL read rejects the late actor, and sixteen timed-out SQL reads retain the capacity limit until settlement.
- `packages/db/src/firebase-identity-repository.ts:19` uses one parameterized SQL snapshot for an approved project/uid mapping, active user, active organization and compatible current membership roles. It neither links by email nor provisions users. Real HTTP/PGlite probes confirmed separate owners under reverse-completing requests, rejection when a mapping is disabled during verification, and a 403/no tenant write when the current platform role is downgraded after the identity snapshot.
- `packages/auth/package.json:13` exposes the new subpath only under the `node` condition. The root barrel does not import it. An independent actual Vite browser resolution rejected that subpath, and all emitted normal/demo/preview JavaScript, source maps, and HTML were free of Firebase Admin/server-credential markers.

**Non-blocking follow-up (P3):** promote the mid-verification emulator/disposal and post-identity SQL role-downgrade probes into durable regression tests when implementing the live server lifecycle. Their behavior passed this independent review, but these additional scenarios currently live only in the review harness; `packages/auth/test/firebase.test.ts:174` primarily covers emulator configuration before a request, and the checked-in HTTP tests change the user role before authentication begins. This is the one-point test-evidence deduction, not an observed authorization failure.
