# Phase 1 Vercel Development Preview Plan

**Goal:** Fulfil the user's explicit request to see the actual service UI on the existing Vercel site while completing Phase 1.

**Authority:** User, 2026-08-31: “어차피 지금 사이트를 누구한테 보여줄것도 아니니까 버셀에도 개발용 미리보기 띄워줘”. This explicitly expands the closeout plan's prior unchanged-Vercel/static-DemoShell constraint. All plan/final-review gates remain mandatory.

**Architecture:** Serve the real `App`/`StudioWorkbench`/`StudentPlay` with its real HTTP client, real Hono application, real repositories, deterministic Rasa and fresh browser-memory PGlite. An injected preview-only HTTP transport forwards requests to Hono in that tab. This is a synthetic development environment under complete client control, not production authentication, server-authoritative public data, or a secure backend. Keep the normal non-preview app fail-closed and keep the old DemoShell available for its regression suite.

**Spec:** `docs/PROJECT_CANON.md`; approved M5/M6 local-provider design; closeout plan and its reviewed amendments; the above current user direction.

## Scope and safety

- No Firebase, real student data, remote database, external AI, credentials, paid resources or serverless API. Existing source repositories remain read-only.
- Database is `memory://`, one instance per active preview runtime. Reset destroys/recreates only this synthetic instance; reload starts fresh. No cookies, localStorage, IndexedDB, or cross-user data.
- Prominent Korean notice: development preview, synthetic accounts/data, this tab only, reset on refresh, deterministic local Rasa. Do not imply signup, secure login, real AI generation or persistent records exist.
- Synthetic teacher/student clients have independent fixed identities; switching UI cannot change in-flight request identities. Existing tenant/role repository checks remain unmodified and run normally, but are educational preview behavior rather than protection against the browser owner.
- Startup is lazy, visibly loading and safely retryable on error. StrictMode/remount must not leak or multiply databases. Reset/role switching must not race in-flight writes into a closed database; disable reset while switching/initializing and close only after outstanding transport work settles, or dispose via a controlled lifecycle.
- Shared `node:crypto` alias is enabled only for the explicit preview build; use Web Crypto `randomUUID` and pinned synchronous SHA-256 from `@noble/hashes` (verify registry version/API before locking). Adapter accepts only actual supported algorithm, UTF-8 updates and hex digest and rejects unsupported usage. No hand-written crypto or general Buffer polyfill.

Construct separate role clients and return scoped IDs, APIs and a controlled close/reset interface. Reuse one initialization promise/owned runtime; no persistent database or global fetch override.
4. **Actual UI wrapper:** create `apps/web/src/dev-preview/development-preview.tsx` and scoped CSS if needed. Include the notice, teacher/student role switch and reset. Provide a sample JSON draft through a narrow optional `StudioWorkbench` input prop or an explicit sample control, without changing normal defaults or pretending a real AI generated it. 5. **Lazy build entry:** `apps/web/src/main.tsx` adds explicit `VITE_DEV_PREVIEW=true` lazy branch with loading/error/retry states. 6. **Vite/assets/dependencies:** preview-only alias in `apps/web/vite.config.ts`; exclude PGlite from unsafe optimizeDeps processing as official guidance requires; emit/copy or explicitly locate its same-origin WASM/data assets with correct MIME and size checks. Test desktop/mobile initialization, teacher sample→validate→sandbox→approve→assign, student wrong→hint→retry→complete, teacher evidence/boss, genuine first-correct and no duplicate effects, role switch state, reset/reload, startup failure recovery, and normal non-preview exclusion. Browser controls must have accessible names and not overflow. Add `test:preview` to CI after the existing full/demo browser gates using the same pinned Chromium install. Avoid tracing/screenshots containing anything except test data.

## Test-first evidence

For injection, an explicitly supplied failing transport must affect the real HTTP client rather than calling global network. For UTF-8 parsing, legal multibyte input must work without Node Buffer and over-limit byte input must still fail. Known hash vector `sha256('abc') = ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad` must match both Node and preview artifact verification. Before changing Vercel flags, browser tests must fail to find the real development preview using the old build. Capture asset/CSP failures as genuine RED, not missing-package test setup.

## Acceptance and delivery

- Root incorporates this plan into the whole Phase 1 gate; browser/preview implementers cannot be final validators of their own change.
- All existing checks and new real-boundary/browser tests pass. Independent final review inspects the entire diff, browser-only security/normal-build exclusion, dependency/CSP changes and actual deployed-build evidence; score >85 with no critical blocker.
- Exact-head CI includes preview browser acceptance, then expected-head merge and merged-result check. Observe the existing Git-linked Vercel Production deployment for the merged SHA and verify the public URL now loads the real development wrapper, assets and a synthetic interaction through the browser. Do not stop at an HTTP200 or old DemoShell screenshot.
- Rollback is a reviewed commit revert or restoring the old build flag/CSP together; no persistent data migration or deletion is involved. Keep the old demo testable. Clearly distinguish Phase 1 development preview from operating-service readiness in final documentation.
