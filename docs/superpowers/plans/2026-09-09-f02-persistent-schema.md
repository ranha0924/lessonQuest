## Scope and interfaces

1. `packages/db/src/migrations/0001.ts` contains an immutable snapshot of the existing schemaSql from `schema.ts`, attributed to base4a0e414, with a hardcoded SHA-256. `packages/db/src/provisioning.ts` is a Node-only export `@lessonquest/db/provisioning`. `migrateLessonQuest(database, runtimeRole)` runs in one transaction, takes a stable advisory transaction lock, checks role safety, and creates only the dedicated `lessonquest` schema if absent. Refuse any preexisting schema without exactly the known version/checksum ledger. An existing known ledger must also have the expected schema objects; no automatic repair, overwrite or down migration. Store version and checksum in an immutable ledger and revoke PUBLIC privileges on the new schema, tables and functions. The migration role owns objects; runtimeRole must already exist, be a different login role, lack superuser/createdb/createrole/bypassrls privileges and not be a member of the migration owner. Parameterize values; validate SQL identifiers with a strict lowercase ASCII pattern before quoting. No user-provided SQL.
2. Grant the runtime role USAGE on the schema, SELECT on users/firebase_identities/organizations/organization_members and the migration ledger, SELECT/INSERT/UPDATE on lesson_inputs, and SELECT/INSERT on lesson_input_mutations/audit_logs. No authorization-row writes, DELETE, DDL, trigger changes or ledger writes. No public grants. Validate effective privileges, including inherited/public privileges, before accepting a repeat migration. Reject unexpected or additional migration versions/checksum drift. Include a schema-object inventory checksum to detect missing/unexpected table/function/trigger objects in the dedicated schema; no assertion of complete semantic tamper detection. Runtime health will separately require this ledger before serving persistent traffic.
3. `PostgresOptions` gains a validated optional schema value restricted to `lessonquest` (default remains existing behavior). The explicit pool startup options set `search_path=lessonquest,pg_catalog`; reject any other input, and keep all prior TLS/URL/error/transaction guarantees. Provisioning uses transaction-local search_path before running the immutable snapshot, so a caller's default search_path cannot target public.
4. `bootstrapTeacher(database, {projectId,uid,organizationName})` is an operator-only Node provisioning function, never an HTTP route. Validate the explicit dedicated project/uid and name; require the known schema/ledger, serialize by project/uid, create an internal UUID TEACHER, an ACTIVE identity mapping and a new private organization with TEACHER membership in one transaction. No SUPER_ADMIN, email matching, first-visitor detection, existing organization joining or role parameter. Repetition returns the same IDs only if the exact active TEACHER mapping/private organization/name/membership remains consistent; disabled, conflicting or multiple existing owned organizations fail closed without repair. Return only internal IDs and a created/unchanged status, not credentials. Initial actual Firebase uid must be explicitly supplied by the operator later.
5. F01 mutation serialization changes from locking an authorization membership row to an advisory transaction lock keyed by actor+tenant, so runtime authorization tables can remain SELECT-only. Hash collisions only over-serialize; authority remains the existing current DB check after lock acquisition. The same actor/tenant requests still serialize across pools and current disable/downgrade checks remain authoritative. No changes to mutation/revision semantics. Test the change with actual PostgreSQL and the restricted runtime role, including a blocked duplicate and revocation while waiting.
6. `scripts/provision-lessonquest.js` exposes only explicit `migrate` and `bootstrap-teacher` commands. Require a separate LESSONQUEST_MIGRATION_DATABASE_URL, explicit expected host/database and fixed target schema; no DATABASE_URL fallback. Reject mismatch before any query, verify TLS through the existing production adapter, require runtime role for migrate and explicit project/uid/name for bootstrap, and close in finally. Print safe result/status or generic failure; never URL, uid, SQL, raw errors or credentials. No migration call in API startup/build. Remote use remains blocked until target identity, isolation and recovery evidence are verified; this script's existence is not authority to run it remotely.

## Recovery and delivery boundary

All migration DDL, grants and ledger writes are transactional; failures leave no partial new schema or authorization grant. Never drop or alter an existing incompatible schema automatically. No automatic destructive rollback is provided. For a fresh remote dedicated database, first confirm its target and absence of real data, create a recoverable Neon branch/checkpoint, verify separate preview isolation and retain the previous application deployment; only then run the reviewed command. Future versions need additive migration plans/checksums and their own gates. Local disposable test resources are owned and removed by the existing harness. Browser Google session/runtime wiring and concrete remote setup follow this prerequisite; this unit does not claim live login/storage or F02 completion.

## Read-only authority refinement

The restricted-role integration test found that F01 update's joined `FOR UPDATE` also required write access on users and organization tables. Narrow this to `FOR UPDATE OF li`, then perform a fresh authorized read after acquiring the lesson row lock and before writing. Add a deterministic regression where an operator holds that lesson row, disables the membership on a separate committed connection while the update waits, then releases the row. The update must refuse and leave revision/content unchanged. This preserves current-authority checks after either serialization or lesson-row waits without granting authorization-table writes.
