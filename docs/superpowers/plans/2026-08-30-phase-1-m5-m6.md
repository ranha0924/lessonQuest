# Phase 1 M5–M6 Implementation Plan

> **For Codex:** REQUIRED SUB-SKILL: Use `superpowers:test-driven-development` while implementing each task, `VibeSec-Skill` for every trust boundary, and `superpowers:verification-before-completion` before claiming completion. Run focused RED/GREEN checks during implementation, one complete implementer verification after all tasks, then one fresh independent final review.

**Goal:** Complete Phase 1 with answer-safe deterministic Rasa hints and one server-authoritative class boss campaign, preserving tenant isolation, append-only evidence, exact retry behavior, and aggregate-only student visibility.

**Architecture:** Strict contracts define every HTTP and persistence boundary. `@lessonquest/rasa` is a pure provider/policy package with no network or secret access. `LearningRepository` remains the authority for attempts, answers, learning events, and sequence allocation; focused `RasaRepository` and `GamificationRepository` own their own tables and workflows. Learning-event commits enqueue boss projection work transactionally, while a separate idempotent drain derives contributions from stored authoritative events. Hono performs authentication/parsing/trace propagation, and React renders only parsed, student-safe responses.

**Tech stack:** TypeScript 6.0.3, Zod 4.5.2, Hono 4.13.5, PGlite 0.5.8, Vitest 4.1.11, React/React DOM 19.2.8, React Testing Library 16.3.3, Vite 8.2.2, pnpm 11.24.0.

**Spec:** `docs/superpowers/specs/2026-08-30-phase-1-m5-m6-design.md`

## Global constraints

- Do not access Firebase, production services, real student data, external AI providers, secrets, existing source repositories, or existing deployments.
- Do not push, merge, open or update a PR, or deploy. All implementation remains on `codex/phase1-m5-m6-complete` until the user separately authorizes external mutation.
- Preserve M1–M4 behavior and data. Schema work is exercised only against fresh local PGlite databases; this slice does not include a production migration.
- Every request body and response is parsed with strict shared schemas. Unknown fields, client-owned tenant identifiers, client damage, correctness, hint level, context, model, token use, cost, or raw provider output fail closed.
- Every protected operation rechecks current database-backed organization role, class membership/ownership, resource tenancy, and lifecycle. Unauthorized and cross-tenant identifiers collapse to the existing safe not-found response.
- Provider input excludes the answer key, option labels, correct option ID, explanation, raw student text, email, credentials, and full profile. Provider output is React text only and is never written through `dangerouslySetInnerHTML`.
- The browser cannot emit `RASA_OPENED`, `HINT_USED`, or `BOSS_DAMAGE_EARNED`. The server alone derives those facts.
- Learning-event durability must not depend on boss projection success. Duplicate requests/events/jobs cannot duplicate usage, actions, sequence increments, or contributions.
- Use exact synthetic UUIDs, injected clocks/IDs, and deterministic local provider fixtures in tests.
- During tasks, run only the named focused test commands. Run the complete verification bundle once after implementation, followed by exactly one fresh independent non-implementing review unless fixes require a new review.

```ts
export interface ExperienceEventSession {
  started(stepId: string): ClientLearningEvent;
  answered(
    stepId: string,
    optionId: string,
    attempt: number,
    elapsedMs: number,
  ): ClientLearningEvent;
  retried(
    stepId: string,
    optionId: string,

Only one envelope may be pending. The implementation uses a short transaction to authorize, construct/hash safe context, calculate the next level, and create/recover the request. The provider runs outside the transaction under a 2-second abort timeout. Terminal replay returns stored output without another provider call.
