## Concurrency refinement after real PostgreSQL RED

The forced-overlap create test reproduced an existing F01 race: both transactions read an absent mutation, then one loses the unique constraint and returns a persistence error. Earlier fast two-pool execution passed accidentally because requests did not overlap at the ledger. Preserve that RED evidence. Extend the bounded runtime change in lesson-input-repository.ts: before create/update authorization and mutation-ledger reads, lock the actor's existing active organization_members row with SELECT ... FOR UPDATE. Recheck the full current creator/teacher authority after obtaining the lock. This serializes writes only for the same actor and organization, closes same-mutation create/update races without adding a table or retrying ambiguous transactions, and keeps unrelated actors/organizations concurrent. Retain revision row locking for competing updates. Test the forced-overlap create and identical update replay plus existing tenant/role tests on both engines. SQL content otherwise stays unchanged; no production DDL.

Also exercise caught SQL failure and termination of an invocation-owned checked-out backend. Keep a safe error listener while the pool client is checked out; a terminated connection is destroyed on release and its failed rollback never replaces the safe/domain error. These are lifecycle requirements already in the original plan.

Lifecycle refinement before fix: a detached failed SQL promise can be queued before COMMIT but settle after the callback. Track all issued transaction-query outcomes, finish the handle, drain pending work, and reject if any failed before COMMIT; this prevents a PostgreSQL ROLLBACK response from being reported as a committed result. The real-PG detached-query regression must fail before the fix and pass afterward.
