# Phase 2 identity export and mapping-readiness design

Date: 2026-09-01

## Purpose

Define and verify the first safe boundary for connecting existing WordQuest accounts to LessonQuest identities. This unit accepts only synthetic, caller-supplied JSON values, validates a versioned read-only identity export and an explicit mapping plan, and produces a deterministic redacted readiness report. It does not read Firebase, open files, query LessonQuest storage, create users or memberships, change authorization, or migrate data.

The unit satisfies the Phase 2 sequencing rule in `docs/INTEGRATION_PLAN_V2.md`: establish `externalAuthId` mapping and a read-only export contract before any real-data dry run, backup, transfer, checksum comparison or rollback rehearsal.

## Chosen approach

Add strict data-transition contracts to `@lessonquest/contracts` and a new side-effect-free `@lessonquest/data-transition` package for canonicalization, hashing and reconciliation. Keeping the format in contracts makes versioning and structural validation reusable. Keeping reconciliation separate prevents identity-transition policy from entering authentication, tenant repositories or the web bundle.

The rejected alternatives are:

- adding `externalAuthId` to the `users` table now, because that starts a schema transition before the source contract and conflict behavior are proven;
- adding a file-reading CLI or Firebase adapter now, because I/O and credentials would widen a synthetic contract-validation unit into an operating migration tool;
- matching accounts or organizations by display name, email or organization label, because those values are mutable, identifying and not tenant authority.

## Versioned inputs

### `WordQuestIdentityExportV1`

The strict export has these fields:

- `format: "lessonquest.wordquest.identity-export"`
- `version: 1`
- `exportId`: UUID generated by the read-only exporter
- `exportedAt`: offset-aware RFC 3339 timestamp
- `sourceSystem: "WORDQUEST_FIREBASE"`
- `sourceCounts`: nonnegative safe integers for `users`, `privateStateDocuments`, `summaryDocuments` and `learningRecords`
- `accounts`: at most 100,000 records containing only:
  - `externalAuthId`: exact opaque provider identifier, 1–128 characters, with no control characters and no leading or trailing whitespace;
  - `legacyOrganizationKey`: exact opaque source scope key, 1–128 characters under the same whitespace/control rule;
  - `sourceRole: "STUDENT" | "TEACHER" | "MASTER"`;
  - `sourceStatus: "ACTIVE" | "DISABLED"`.

The contract deliberately excludes display names, email addresses, tokens, Firebase configuration, raw private state, per-student learning content and organization display labels. `sourceCounts` preserves nonidentifying reconciliation anchors without claiming that legacy learning records already have LessonQuest event semantics.

Structural validation is strict and bounded. It rejects unknown fields, malformed versions and invalid scalar values. It does not silently trim opaque identifiers. Duplicate and conflicting records remain parseable so the readiness report can describe every semantic blocker in one deterministic pass.

### `IdentityMappingPlanV1`

The strict plan has these fields:

- `format: "lessonquest.identity-mapping-plan"`
- `version: 1`
- `sourceExportChecksum`: a `sha256:<64 lowercase hex>` value that binds the plan to one canonical source export;
- `accountMappings`: at most 100,000 exact pairs of `externalAuthId` and LessonQuest `userId` UUID;
- `organizationMappings`: at most 100,000 exact pairs of `legacyOrganizationKey` and LessonQuest `organizationId` UUID.

The mapping plan carries no role assignment. A source record can identify a proposed canonical account and organization, but cannot grant authority. In v1, `STUDENT` and `TEACHER` produce proposed target roles with the same least-privilege meaning. `MASTER` always produces the blocking finding `PRIVILEGED_ROLE_REQUIRES_REVIEW`; it never implies `ORG_ADMIN` or `SUPER_ADMIN`.

One external account may map to one canonical user, and one canonical user may map to one external account. One legacy organization key may map to one canonical organization, and v1 refuses to merge multiple legacy keys into one canonical organization. Any later consolidation requires its own reviewed policy.

## Canonical checksums

`canonicalizeWordQuestIdentityExport` and `canonicalizeIdentityMappingPlan` validate first, then create a stable JSON representation with lexicographically ordered object keys and deterministically sorted record arrays. The canonical form preserves exact opaque identifier bytes and includes all versioned fields. SHA-256 over the UTF-8 canonical form produces `sha256:<64 lowercase hex>`.

Reordering otherwise identical accounts or mappings must not change a checksum. Changing metadata, a count, an identifier or a mapping must change it. The implementation uses Node's built-in crypto only and introduces no dependency.

## Reconciliation and report

`reconcileIdentityExport(exportInput, mappingInput)` parses both inputs, verifies the plan's source checksum, and performs a complete deterministic semantic pass. It returns a strict `IdentityReadinessReportV1` containing:

- the report format/version;
- source and mapping checksums;
- input counts, mapped account count and ready account count;
- proposed target-role totals for nonprivileged roles;
- `ready: true` only when no blocker exists;
- findings sorted by code, record index and fingerprint.

Findings cover at least:

- source checksum mismatch;
- duplicate external account records;
- duplicate account mappings;
- multiple external accounts mapped to one canonical user;
- duplicate organization mappings;
- multiple legacy organizations mapped to one canonical organization;
- unmapped external account;
- unmapped legacy organization;
- account or organization mapping unused by the bound export;
- conflicting duplicate source records;
- `MASTER` privilege review;
- source-count mismatch where `sourceCounts.users` differs from the number of unique exported accounts.

A finding identifies source values only by `sha256:<64 lowercase hex>` fingerprints plus array indexes. It never emits raw `externalAuthId` or `legacyOrganizationKey`. The report may include canonical LessonQuest UUIDs because it is an operator-side dry-run artifact, but it contains no display names, emails, content or credentials.

Any parse failure throws a bounded public validation error without echoing the rejected input. Semantic problems return a complete report with `ready: false`; they never partially apply a mapping. Unexpected failures propagate to the caller, and no retry or persistence occurs inside the package.

## Package and file boundaries

- `packages/contracts/src/data-transition.ts`: strict schemas and inferred public types only.
- `packages/contracts/test/data-transition.test.ts`: structural bounds, unknown-field rejection and type contract tests.
- `packages/data-transition/src/canonical-json.ts`: local stable JSON and SHA-256 helpers.
- `packages/data-transition/src/identity-reconciliation.ts`: pure canonicalization and readiness policy.
- `packages/data-transition/src/index.ts`: public exports only.
- `packages/data-transition/test/fixtures/wordquest-identity-export-v1.json`: fully synthetic export.
- `packages/data-transition/test/identity-reconciliation.test.ts`: checksum, conflict, privacy and determinism cases.
- workspace build scripts and documentation: add the package to normal verification without importing it into API, auth, DB or web runtime code.

The package may depend on `@lessonquest/contracts` only. It has no filesystem, Firebase, HTTP, database, environment-variable or browser API boundary.

## Test and acceptance design

Test-first implementation must demonstrate these RED cases before adding behavior:

1. strict v1 schemas and package exports do not exist;
2. a complete synthetic export and mapping plan cannot produce a ready report;
3. reordered arrays cannot yet prove identical checksums;
4. malformed, unknown-field and oversized inputs are not rejected;
5. duplicate external accounts, canonical-user collisions, organization collisions, missing/unused mappings, count mismatches and `MASTER` are not reported fail-closed;
6. findings cannot yet prove raw source identifiers are absent;
7. no regression suite yet proves the package has no runtime coupling to auth, DB, API, web or Firebase.

GREEN acceptance requires focused contract/package tests, full workspace check, integration and E2E regressions, production dependency audit and diff checks. Browser behavior is unchanged, so existing demo and service-preview suites must remain green and the normal web build must not include the data-transition package. All fixtures use obviously synthetic identifiers.

## Security, privacy and tenant rules

- Source organization keys are lookup inputs, never authorization evidence.
- No automatic matching by name, email or source role occurs.
- No source role can grant `ORG_ADMIN` or `SUPER_ADMIN`; `MASTER` blocks readiness.
- Structural errors and ambiguous mappings fail closed.
- Raw source identifiers may exist only in the caller-owned input and mapping values. They do not enter findings, logs, documentation fixtures outside the checked-in synthetic example, or browser assets.
- The implementation never accesses Firebase, real student data, a reference deployment, a persistent database or credentials.
- Existing WordQuest and LessonQuest deployments remain unchanged until the normal reviewed delivery step; no manual data operation is authorized by this design.

## Containment and later work

This unit is reversible by removing the contracts/package and reverting documentation. It creates no schema, stored record or external resource. If validation fails, the caller fixes a copy of the export or mapping plan and reruns the pure reconciliation; LessonQuest and WordQuest state remain untouched.

Explicitly deferred work includes a Firebase read-only exporter, file/CLI I/O, a persistent external-identity table, local or production schema changes, membership creation, real-data dry runs, per-record learning transformation, user/learning aggregate transfer checks, backups, rollback rehearsal and any write to WordQuest or LessonQuest data. Each requires a later plan and, where real data or destructive risk is involved, separate user approval.

## Provenance

The schemas, canonicalization and reconciliation policy are original LessonQuest work derived from the approved product and integration requirements. No source code or data from WordQuest is copied. The synthetic fixture exists only to prove the LessonQuest contract.
